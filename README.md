# local-ai-phone-assistant

Локальный голосовой ассистент: телефон слушает постоянно, «мозг» живёт на домашнем
ПК. Ничего не уходит в облако — LLM, распознавание речи и синтез голоса работают
офлайн на вашем железе.

```
┌─────────────────────┐   Wi-Fi (LAN)   ┌──────────────────────────────────┐
│  Android-телефон    │ ──────────────► │  ПК (без GPU, Python 3.12)       │
│  • wake word (Vosk) │   WebSocket /   │  • llama.cpp + LLM (порт 8080)   │
│  • запись речи      │   HTTP REST     │  • server.py  — API (порт 8090)  │
│  • озвучка ответа   │ ◄────────────── │  • kokoro-ru  — TTS (порт 8091)  │
│  • кнопки/интерфейс │   WAV + JSON    │  • faster-whisper — STT (CPU)    │
└─────────────────────┘                 └──────────────────────────────────┘
```

Вне дома то же самое работает через зашифрованный туннель `tunnel.py`
(порт 8443, см. «Доступ из интернета»).

## Возможности

- **Постоянное слушание**: wake word («Гемма») распознаётся на телефоне офлайн
  (Vosk, ограниченная грамматика — только слово-триггер), дальше речь стримится
  на сервер. Голосовая модель `vosk-model-small-ru-0.22` **встроена в APK**
  (Apache 2.0) и распаковывается при первом запуске — без скачивания.
- **Диалог**: контекст из последних реплик, уточнения («а завтра?»), follow-up
  запросы в течение короткого окна после ответа.
- **Профили характера с голосами** (переключение голосом: «профиль цундере»):

  | Профиль | Голос | Пол |
  |---|---|---|
  | Цензурный | dima | мужской |
  | Нецензурный | dima | мужской |
  | Цундере | sveta | женский |
  | Яндере | masha | женский |
  | Куудере | dima | мужской |
  | Дередере | masha | женский |

  Пол ассистента выводится из голоса озвучки и задаётся в system-промпте:
  на «ты мужчина или женщина?» он отвечает в роде своего голоса.
- **Распознавание команд профиля**: точные стемы + нечёткое сопоставление
  (difflib) — STT может коверкать имена («Дэри Дэра», «нетнзурный»,
  «сундейра»), и команда всё равно выполняется.
- **Действия с подтверждением**: отправка сообщений в Telegram/VK и звонки
  выполняются только после голосового/кнопочного подтверждения (окно ~30 с).
- **Поиск в интернете** (DuckDuckGo по умолчанию, без API-ключей) с кратким
  голосовым пересказом найденного.
- **Звонки**: поиск контакта в телефонной книге и набор номера.
- **Озвучка**: kokoro-ru (sidecar, несколько русских голосов) с фолбэком на
  Piper.
- **Надёжность**: VAD-фильтр тишины, детект конца фразы, повтор verify при
  ложном wake, подавление обработки во время озвучки.
- **Доступ из интернета**: собственный WSS-туннель с токеном и пиннингом
  сертификата — без Tailscale/VPS и без системного VPN на телефоне.

```
  start-kokoro.ps1        запуск TTS-sidecar

  server.py               FastAPI: точка входа, /ask /voice /ws_voice /tts /confirm...
  tunnel.py               туннель: wss://:8443/tunnel -> прокси на 8090 (доступ из интернета)
```

Python-модули лежат плоско внутри `server/` (плоские импорты `import llm`
и пути `Path(__file__).parent` для `.env`/моделей/данных), поэтому
`.env`, окружения `.venv`/`.venv-tts` и каталог `models/` создаются там же.
Пакет `llm/` — единственное вложенное исключение (импорт `import llm`
подхватывает пакет).

## Требования

- **ПК**: Windows, Python 3.12, без GPU (всё на CPU), llama.cpp с запущенной
  моделью на порту 8080.
- **Телефон**: Android 8.0+ (minSdk 26). Дома — в той же Wi-Fi-сети, что и ПК;
  вне дома — мобильный интернет (основной путь — IPv6, запасной — IPv4 через
  проброс порта 8443, см. «Доступ из интернета»).
- **Сеть**: дома телефон должен достучаться до портов 8090 (API) и 8080 (LLM);
  из интернета — только до 8443 (зашифрованный туннель).

## Установка сервера

```powershell
# 1. Клонировать репозиторий и перейти в каталог Python-части

# 2. Основное окружение
python -m venv .venv
.venv\Scripts\pip install -r requirements.txt

# 3. Окружение для TTS-sidecar (kokoro-ru)

# 4. Голоса Piper (фолбэк озвучки)
```

Модель для llama.cpp (Gemma/Qwen-класс, квантованная) кладётся в llama.cpp
отдельно — этот репозиторий модель не содержит.

## API

Все эндпоинты, кроме `/health` и `/cert`, требуют заголовок
`X-Gemma-Token` со значением `ASSISTANT_API_TOKEN` (401 без него).
Через туннель токен добавляется приложением автоматически.

| Метод | Путь | Тело | Ответ |
|---|---|---|---|
| GET | `/health` | — | `{"status","model","stt_model","tts_engine",...}` |
| GET | `/cert` | — | `{"fingerprint_sha256","pin"}` — пин сертификата туннеля (для телефона) |
| POST | `/ask` | `{"text":"..."}` | `{"reply","action","args","needs_confirm","token","elapsed_ms"}` |
| POST | `/voice` | multipart `file` (wav/ogg/webm/m4a) | как `/ask` + `{"text","stt_ms"}` |
| WS | `/ws_voice` | стрим аудио-чанков | события конца фразы → готовый ответ |
| POST | `/tts` | `{"text":"...","voice":"..."}` | WAV (`audio/wav`), голос берётся из профиля |
| POST | `/confirm` | `{"token":"...","yes":true\|false}` | `{"reply","ok"}` |
| GET | `/profile` | — | текущий профиль, голос, список доступных |
| POST | `/profile` | `{"profile":"tsundere"}` | переключение профиля |
| GET | `/update/manifest` | — | манифест релиза APK: `{"version_code","version_name","file","size_bytes","sha256","released_at"}` |
| GET | `/update/apk` | — | скачивание APK (`application/vnd.android.package-archive`), имя из поля `file` манифеста |
| POST | `/debug/log` | `{"entries":[{"ts","level","tag","msg"}]}` | приём логов телефона в `server/logs/phone.log` (1…200 записей, тело ≤ 256 КБ) |

`action`: `search` | `send_tg` | `send_vk` | `call` | `none`.
Отправка сообщений и звонки выполняются **только** после `/confirm` с
`yes:true` (окно подтверждения ограничено `ASSISTANT_CONFIRM_TTL`).

### Стриминговый конвейер `/ws_voice`

Ответ озвучивается **по мере генерации**, а не после полного готового текста:

1. LLM стримится через `llm.chat_stream()`; инкрементальный парсер
   (`_StreamParser`) вырезает законченные предложения из поля `reply` и
   отдельно ловит поле `query` (поисковый запрос для спекулятивного поиска).
2. Каждое предложение уходит в TTS (kokoro-ru), и WAV-чанк сразу летит
   телефону событием `audio`; текст — событием `sentence`.
3. **Спекулятивный поиск**: поле `query` из первого токена запускает поиск
   заранее (кэш 180 с, таймаут 15 с) — когда приходит `needs_confirm`,
   готовый результат уже в `/confirm`, не дожидаясь таймаута.
4. Телефон играет чанки по очереди (`chunkQueue`) под SPEAK_LOCK, уважая
   стоп-слово и паузу барж-ин; финальный `reply` с флагом `streamed=true`
   повторно НЕ озвучивается.

Замеры (ПК без GPU, Gemma-4-E4B): первый токен ~1 с, первый звук ~3.5 с
от старта LLM (раньше — 6–15 с после полного ответа).

## Android-приложение

Kotlin-клиент (`android/`), foreground service с доступом к микрофону:

- распознаёт wake word офлайн через **Vosk** (модель встроена в APK и
  распаковывается при первом запуске),
- записывает речь и стримит её на сервер (`/ws_voice`), проигрывает ответ (WAV),
- поддерживает Bluetooth-аудио и системную громкость озвучки,
- экран: адрес сервера, DDNS-домен туннеля, токен API и пин сертификата —
  на отдельном экране **«Настройки»** (иконка-шестерёнка в шапке, там же
  кнопка «Проверить связь» — пинг `/health` по LAN), на главном — статус
  сервиса, круглая кнопка Старт/Стоп
  (состояние синхронизируется с сервисом, пульсирует вместе с волнами-кольцами)
  и выбор профиля характера. Интерфейс — стеклянные карточки на лавандовом
  фоне (Theme.Gemma + Material3).

Кнопка **Старт** работает в двух режимах (гибридный туннель):

1. дома: пинг `GET /health` по LAN (1.5 с) → сервис поднимается по LAN, а
   заодно телефон забирает пин сертификата (`GET /cert`, TOFU);
2. дома нет: поднимается канал `wss://<ddns>:8443/tunnel` (автопереподключение
   с backoff 1→30 с), `/health` проверяется уже через него, статус на экране —
   «🌐 Из интернета — туннель подключён» / «🔄 Переподключение…» /
   «⛔ Нет связи…». **Стоп** останавливает сервис и закрывает канал.

Вся логика переключения LAN/туннель — автоматическая (`ServerClient` сам
выбирает транспорт), ручных переключателей нет.

Сборка и установка (adb не обязан быть в PATH):

```powershell
$env:JAVA_HOME = '<путь-к-jdk-17>'
cd android
.\gradlew.bat assembleDebug

# Установка на подключённый телефон:
$adb = "$env:LOCALAPPDATA\Android\Sdk\platform-tools\adb.exe"
& $adb push app\build\outputs\apk\debug\app-debug.apk /data/local/tmp/app.apk
& $adb shell pm install -r -d /data/local/tmp/app.apk
```

Адрес сервера вводится на экране «Настройки» (шестерёнка в шапке; по
умолчанию подсказка `http://192.168.1.100:8090` — замените на IP вашего ПК).

## Обновление приложения

Телефон забирает новую сборку с домашнего ПК **по LAN** — без провода и adb:
скрипт кладёт APK в каталог релизов, а приложение само проверяет наличие
новой версии, скачивает файл (сверяет размер и SHA-256) и запускает
системный установщик.

**Требования:**

- на ПК запущен `server.py`, и телефон видит его в той же сети;
- `ASSISTANT_API_TOKEN` одинаковый в `.env` и в настройках приложения —
  оба запроса идут под заголовком `X-Gemma-Token`;
- собранная сборка лежит в `releases/` (заполняет `scripts/build-apk.ps1`:
  `app-debug.apk` + `manifest.json` с версией, размером и sha256);
- обновление идёт **только по прямому LAN-адресу** сервера — через туннель
  не работает: `Updater` делает обычный HTTP-запрос и канал туннеля
  не поднимает. Вне дома (8090 напрямую недоступен) обновиться нельзя —
  это ограничение схемы, а не поломка.

**Регламент релиза** (повторяемо с нуля):

```powershell
# 1. Поднять версию в android/app/build.gradle.kts (versionCode +1, versionName)
# 2. Собрать и опубликовать:
powershell -ExecutionPolicy Bypass -File scripts\build-apk.ps1
# 3. Перезапускать server.py не нужно — эндпоинты читают каталог при каждом запросе
# 4. На телефоне: Настройки → Обновление → «Проверить обновление» → «Скачать и установить»
```

На шаге 4 карточка «Обновление» (экран «Настройки») показывает подпись
текущей версии, дальше ведёт по состояниям: «Проверить обновление» →
«Доступна версия X (код N)» → «Скачать и установить» (прогресс, потом сверка
размера и sha256) → «Установить» — открывается системный установщик Android.

**Ограничения:**

- сборка **debug** и подписана debug-ключом: поверх установленной сборки
  Android ставит только APK с тем же ключом подписи — если телефон и ПК
  собираются разными debug-ключами, установка поверх откажется;
- APK ~69 МБ — внутрь встроена голосовая модель Vosk;
- каталог `releases/` не попадает в git — это локальные артефакты ПК;
- обновление работает только по LAN (см. выше), через туннель — нет;
- `versionCode` обязан расти: приложение сравнивает `version_code` манифеста
  со своим и отклоняет сборку с кодом ≤ текущего («Установлена последняя
  версия»).

**Проверка после релиза** — манифест отдаёт новый код версии:

```powershell
# curl.exe, а не curl: в PowerShell 5.1 curl — алиас Invoke-WebRequest без -H
curl.exe -H "X-Gemma-Token: <ASSISTANT_API_TOKEN>" http://127.0.0.1:8090/update/manifest
# {"version_code": 2, "version_name": "0.2", "file": "app-debug.apk",
#  "size_bytes": 68801417, "sha256": "...", "released_at": "..."}
```

Пример приведён после подъёма версии — фактические значения всегда в
`releases/manifest.json`.

Пустой `ASSISTANT_API_TOKEN` — заголовок не нужен (LAN-only режим). При
заданном токене: без заголовка — 401; без `releases/manifest.json` — 404
с подсказкой «собери релиз через scripts/build-apk.ps1».

## Беспроводной дебагинг

Отладка телефона без USB-кабеля: отладочные сборки ставятся по Wi-Fi, логи
приложения читаются на ПК. Два независимых канала: Wi-Fi ADB (adb по IP) и
живые логи на сервере (вообще без adb). Телефон и ПК — в одной Wi-Fi-сети.

В примерах `<ip>` — адрес телефона в локальной сети (на телефоне: Настройки →
Wi-Fi → текущая сеть → IP-адрес). `adb` в примерах — это
`%LOCALAPPDATA%\Android\Sdk\platform-tools\adb.exe`, если каталог не добавлен
в PATH (см. «Android-приложение»).

### 1. Разовая подготовка по USB

Один раз подключи телефон по USB и включи сетевой режим adb:

```powershell
adb tcpip 5555
```

Кабель можно отключить (на Huawei/EMUI — только после настроек из §9, иначе
порт закроется через секунды). **Скрипт `wireless-debug.ps1` сам `adb tcpip` не
запускает** — команда требует USB-кабеля; при выключенном режиме скрипт лишь
печатает эту инструкцию. Повторять шаг нужно после перезагрузки или
переподключения Wi-Fi на Huawei/EMUI — режим tcpip там сбрасывается, это
нормально (см. §9).

### 2. Подключение по Wi-Fi

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\wireless-debug.ps1 -Action connect -Ip <ip>
adb devices                                   # ожидаем: <ip>:5555  device
```

Если в `adb devices` не `device`:

- **`offline`** — adb видит телефон, но транспорт мёртв: подожди 2–3 с и
  повтори; не помогло → `adb kill-server`, `adb start-server`, снова
  `connect` (так бывает при слабом Wi-Fi или смене IP телефона);
- **`unauthorized`** — телефон не принял этот ПК: разблокируй экран и
  подтверди запрос «Разрешить отладку по USB?»; если запроса не появляется —
  Настройки разработчика → «Отозвать авторизации USB-отладки» и повтори один
  раз по USB.

Почему не подключается — диагностика с вердиктом:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\wireless-debug.ps1 -Action status -Ip <ip>
```

### 3. Установка отладочной сборки по воздуху

```powershell
cd android
.\gradlew.bat assembleDebug
adb -s <ip>:5555 install -r -d app\build\outputs\apk\debug\app-debug.apk
cd ..
```

### 4. Логи по Wi-Fi (logcat)

```powershell
adb -s <ip>:5555 logcat -v time                                  # живой поток
adb -s <ip>:5555 logcat -d | findstr ru.gemma.assistant   # строки приложения
adb -s <ip>:5555 logcat -b crash -d                              # краши
```

### 5. Живые логи на ПК без adb

Когда кабель не подключён и порт 5555 закрыт, приложение может само
отправлять свои логи на сервер (запрос уходит под заголовком `X-Gemma-Token`
со значением `ASSISTANT_API_TOKEN`):

1. на телефоне: Настройки → **«Логи на ПК»** → вкл (по умолчанию выключен;
   канал требует `BuildConfig.DEBUG`, а публикуемые нами APK — debug-сборки,
   так что реально канал открывает только этот переключатель);
   канал стартует вместе с сервисом (`AssistantService`), поэтому события
   `MainActivity` (например, TOFU-подтверждение сертификата при первом
   запуске) в `server/logs/phone.log` не попадают, даже когда переключатель включён;
2. на ПК при запущенном `server.py`:

```powershell
Get-Content server\logs\phone.log -Wait
```

- события появляются почти сразу: приложение шлёт пачки раз в 2 с;
- формат строки: `[2026-11-07T10:12:33.501] I/AssistantService: transition WAKE -> COMMAND`
  (время ISO-8601, уровень, тег, текст);
- файл `server/logs/phone.log` создаётся при старте `server.py`, ротация 5 МБ × 3
  бэкапа;
- адрес — только LAN-сервер: через туннель логи не отправляются;
- **LAN-guard**: отправка идёт только на приватный/loopback-адрес по `http`
  (или на любой адрес по `https`); если в «Адрес сервера» указан публичный
  хост по `http` — отправка логов приостанавливается, событие «адрес не
  LAN» видно сразу в logcat (не чаще раза в 60 с), а в `phone.log` — только
  после восстановления адреса отправки; записи ждут в буфере. Это осознанное ограничение
  безопасности (CWE-319): пакет логов содержит транскрипты и токен;
  по http не отправляется весь IPv6, кроме loopback (в т.ч. ULA/link-local
  и глобальный) — используйте IPv4-LAN либо https; дефолт и документация —
  IPv4;
- **Лимиты `/debug/log` только размерные** (≤200 записей, ≤256 КБ);
  частотных лимитов нет осознанно — при пустом `ASSISTANT_API_TOKEN` открыт
  весь API (включая `/ask`), модель угроз LAN-first;
- когда закончил — переключатель выключить, записи перестанут приходить.

### 6. Обязательно закрой порт после работы

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\wireless-debug.ps1 -Action disconnect -Ip <ip>
Test-NetConnection <ip> -Port 5555          # ожидаем: TcpTestSucceeded: False
```

- **закрытие идёт командой `adb usb` через доступный транспорт и не требует
  кабеля, если жива Wi-Fi-сессия**: скрипт шлёт `adb -s <ip>:5555 usb` прямо
  по TCP — adbd перезапускается в USB-режиме, слушатель 5555 гаснет сам,
  и только после этого отсоединяется локальный транспорт (`adb disconnect`);
  кабель нужен лишь тогда, когда Wi-Fi-сессии уже нет (тогда обычный
  `adb usb` по USB, а при полном отсутствии транспорта скрипт предупредит);
- **без `-Ip` скрипт выведет подсказку (usage), но fail-safe `adb usb`
  (адрес для него не нужен) выполняется и в этой ветке; код выхода `0`,
  если `adb usb` выполнился (с подключённым телефоном он закрывает порт),
  и `1`, если `adb usb` не выполнился — тогда порт 5555 мог остаться
  открытым. Само закрытие здесь не проверяется (адреса телефона нет) —
  подтверди его позже командой `status -Ip <ip>`**;
- adbd в tcpip-режиме слушает **все интерфейсы телефона**, а не только ваш
  ПК: в чужой или публичной Wi-Fi-сети порт 5555 обязательно закрывай
  (`-Action disconnect`) — иначе отладочные команды по сети доступны любому
  в этой сети;
- на Android ≥ 8 (minSdk 26) первое подключение из нового ПК всё равно
  требует одноразового подтверждения RSA-ключа на экране телефона —
  без него `adb` телефон не использует, даже если порт открыт;
- пока порт открыт, телефон принимает отладочные команды по сети — закрывай
  после каждой сессии; обрыв скрипта может оставить его открытым;
- Huawei/EMUI: режим tcpip сбрасывается после переподключения Wi-Fi или
  перезагрузки — тогда заново разовый `adb tcpip 5555` по USB; а если порт
  закрывается сам через секунды после снятия кабеля — см. §9 (там нужны две
  настройки разработчика). Закрытие порта по Wi-Fi-сессии (п. 1 выше) на
  EMUI после этих настроек работает так же, без кабеля.

### 7. Коды выхода скрипта

| Код | Когда |
|---|---|
| `0` | успех; также всегда `0` у `status` (кроме случая, когда `adb` не найден — тогда `1`), в т.ч. битый `-Ip` — это диагноз, а не сбой, у `usage` для `connect` и у `disconnect` без `-Ip`, если `adb usb` выполнился (само закрытие порта в этой ветке не проверяется — подтверждай `status -Ip <ip>`) |
| `1` | цель не достигнута (не подключилось, порт остался открытым, `adb usb` при `disconnect` без `-Ip` не выполнился) либо `adb` не найден |

Если `adb` не найден — установи Android SDK platform-tools
(`%LOCALAPPDATA%\Android\Sdk\platform-tools\adb.exe`) либо добавь каталог с
`adb.exe` в PATH и повтори команду.

### 8. Сеть и фаервол

Ничего настраивать не нужно: соединение идёт **от ПК к телефону**
(исходящее), скрипт не создаёт и не меняет правил фаервола, входящие порты
на ПК не открываются.

### 9. Huawei/EMUI: порт закрывается сразу после снятия кабеля

**Симптом.** На Huawei/EMUI (проверено на Mate X3, ALT-L29, EMUI 14.2.0,
Android 12/API 31) после `adb tcpip 5555` снятие USB-кабеля закрывает порт
5555 через 2–10 секунд: `adb connect <ip>:5555` перестаёт отвечать,
`adb mdns services` пустеет. Сам tcpip-режим при этом не сбрасывается —
`service.adb.tcp.port` остаётся заданным:

```powershell
adb shell settings get global service_adb_tcp_port   # ожидаем: 5555
```

**Причина (диагностирована по logcat).** При физическом отключении кабеля
EMUI переключает USB-конфигурацию: `Setting USB config to
hisuite,mtp,mass_storage` — уже **без `,adb`**. init останавливает adbd,
процесс слушателя 5555 умирает, живые TCP-сессии рвутся, mdns-объявление
исчезает. То есть штатный сценарий «tcpip → снять кабель → connect» без
дополнительной настройки на таком устройстве не работает.

**Обход — две настройки в «Настройки → Система → Для разработчиков»:**

1. включить **«Разрешить отладку по USB в режиме только зарядка»**
   (в англ. прошивке — «Allow ADB debugging in charge only mode»);
2. снять галку **«Всегда запрашивать при подключении к USB»** («Always prompt
   when connecting to USB»).

Что видно в `settings get global` после настройки:

```powershell
adb shell settings get global allow_charging_adb    # ожидаем: 1
adb shell settings get global usb_conn_prompt       # ожидаем: 0
```

**Порядок операций после настройки** (штатный, кабель снимается последним):

```powershell
adb tcpip 5555                          # при воткнутом кабеле
adb connect <ip>:5555                   # тоже при кабеле — порт открыт
# теперь снять кабель, дальше только по Wi-Fi:
adb devices                             # ожидаем: <ip>:5555  device
Test-NetConnection <ip> -Port 5555      # ожидаем: TcpTestSucceeded: True
adb mdns services                       # ожидаем: <serial> _adb._tcp <ip>:5555
```

Проверено живьём: после снятия кабеля TCP-сессия, порт и mdns живут по Wi-Fi
(сессия жива 12+ секунд наблюдения, `Test-NetConnection` → True).

Примечания:

- **пункта «Беспроводная отладка / Wireless debugging» на EMUI нет** — Huawei
  официально не даёт его в настройках разработчика на EMUI 10–15
  (подтверждено и на этом устройстве; страница поддержки Huawei). Это норма,
  а не неисправность — работает описанный выше Wi-Fi ADB по `adb tcpip`;
- после переподключения Wi-Fi или перезагрузки на EMUI tcpip-режим
  сбрасывается — заново разовый `adb tcpip 5555` по USB и повтор `connect`
  (см. §1; это норма, подсказку об этом печатает и скрипт);
- закрытие порта после работы (§6) после этих настроек идёт **без кабеля**:
  `-Action disconnect` шлёт `adb -s <ip>:5555 usb` по живой Wi-Fi-сессии,
  adbd уходит в USB-режим, слушатель гаснет сам, и только потом выполняется
  `adb disconnect`.

## Доступ из интернета (гибридный туннель)

Своя зашифрованная сессия **внутри приложения** вместо системного VPN:
телефон не поднимает `VpnService`, ничего не спорит с чужими VPN на
телефоне, а наружу торчит ровно один закрытый порт — 8443.

```
┌────────────────────────────┐        wss://<ddns>:8443/tunnel        ┌─────────────────────────────┐
│ Android-телефон            │ ─────────────────────────────────────► │ ПК                          │
│  TunnelClient             │  TLS (самоподписанный сертификат,      │  tunnel.py                  │
│   • пиннинг SHA-256        │   пинится на телефоне) + токен        │   • uvicorn + SSL, :8443    │
│   • keepalive 25 с         │  JSON-рамки req/res (base64-body)     │   • прокси -> 127.0.0.1:8090│
│   • реконнект 1→30 с       │ ◄────────────────────────────────────► │   • сабстрим /ws_voice      │
│  ServerClient/VoiceStream  │  сабстрим /ws_voice (голос, PCM)      │  server.py :8090 (LAN+токен)│
└────────────────────────────┘                                       │  ddns-update.ps1 → dynv6    │
                                                                     └─────────────────────────────┘
```

Только трафик ассистента идёт по туннелю, весь прочий трафик телефона
идёт мимо. Дома приложение по-прежнему ходит напрямую по LAN.

### Установка (пошагово, один раз)

```powershell
# 1. Токен: задан в server\.env (ASSISTANT_API_TOKEN) — впиши его же в приложение
# 2. DDNS: заведи бесплатную зону на https://dynv6.com, впиши в server\.env
#    ASSISTANT_DDNS_HOSTNAME=mypc.dynv6.net и ASSISTANT_DDNS_TOKEN=<токен>
# 3. AAAA/A-запись: задача планировщика каждые 5 минут
powershell -ExecutionPolicy Bypass -File scripts\setup-ddns-task.ps1
# 4. Фаервол (админ): правило входящего 8443 добавляет setup-firewall.ps1
powershell -ExecutionPolicy Bypass -File scripts\setup-firewall.ps1
# 5. Сертификат создаёт tunnel.py сам при старте (SAN: DDNS-имя + localhost)
# 6. Перезапуск стека (поднимет tunnel.py на 8443)
powershell -ExecutionPolicy Bypass -File scripts\start-all.ps1
```

### Диагностика сети (одноразово)

```powershell
powershell -ExecutionPolicy Bypass -File scripts\diag-network.ps1
```

Скрипт покажет публичные IPv4/IPv6, поднимет временный слушатель на 8443 и
выведет адреса внешних порт-чекеров — открой их **с телефона** (мобильный
интернет, Wi-Fi выкл) и убедись, что порт виден:

- **входящий IPv6 работает** — основной транспорт готов;
- **IPv6 закрыт роутером** — сними его «IPv6-фаервол» / «защиту от сетевых
  атак» в веб-морде роутера для этого ПК;
- **IPv4**: нужен белый адрес или проброс — в веб-морде роутера добавь
  переадресацию внешнего TCP 8443 → <LAN-IP ПК>:8443 (правило фаервола
  setup-firewall.ps1 уже открыто для всех профилей);
- **ничего не работает** (нет входящего IPv6 и нет белого IPv4) — без
  Tailscale/VPS этот план не работает: выбирай другой транспорт.

### Настройка телефона

1. На экране «Настройки» (⚙ в шапке) введи адрес сервера (LAN), DDNS-домен,
   `ASSISTANT_API_TOKEN`;
2. **дома** нажми Старт один раз — телефон подтянет пин сертификата
   (`GET /cert`, TOFU) и сохранит его;
3. вне дома жми Старт: «🌐 Из интернета — туннель подключён» → говори «Гемма»
   как обычно. Если приложение ставится сразу вне дома — введи пин
   (`sha256/…`, его отдаёт `GET /cert` на ПК) руками.

### Проверка туннеля с ПК

```powershell
curl -k https://127.0.0.1:8443/health                  # жив ли процесс
curl -k "https://<ddns>:8443/health"                    # снаружи (IPv6 сети)
# полный smoke (auth + прокси + голосовой сабстрим) — вручную через wss://
```

### Ограничения и риски туннеля

| Риск | Что делать |
|---|---|
| Сеть телефона без IPv6 | главный риск; сначала включи IPv4-проброс, иначе — другой транспорт |
| Смена префикса провайдера | `ddns-update.ps1` каждые 5 мин + автопереподключение канала |
| Регенерация сертификата (добавили DDNS-имя) → пин сломался | дома нажать Старт заново (TOFU обновит пин) или вписать новый вручную |
| Неверный токен | канал не открывается («err: bad token»), запросы без заголовка — 401 |
| Оверхед base64 ~33% на WAV | приемлемо; голос идёт сабстримом внутри того же канала |

## Константы таймингов

Телефон (`AssistantService.kt`):

| Константа | Значение | Назначение |
|---|---|---|
| `CONFIRM_MS` | 30 000 | окно подтверждения действия |
| `QUIET_END_MS` | 3 000 | тишина, после которой фраза считается законченной |
| `MAX_COMMAND_MS` | 20 000 | предел длины команды |
| `NO_INPUT_MS` | 10 000 | ожидание речи после wake |
| `MIN_SPEECH_MS` | 1 500 | минимум речи, чтобы обрабатывать |
| `SPEECH_RMS` / `WAKE_MIN_RMS` | 330 / 120 | пороги громкости (речь / wake) |
| `VERIFY_RETRY_MS` | 1 500 | окно повторного wake после ложного срабатывания |
| `FOLLOWUP_START_MS` / `FOLLOWUP_TRIG_MS` | 5 000 / 300 | follow-up запросы после ответа |
| `MAX_FOLLOWUP` | 10 | максимум follow-up подряд |

Сервер (`server.py`, конвенции `/ws_voice`):

| Константа | Значение | Назначение |
|---|---|---|
| `_WS_QUIET_MS` | 1 300 | тишина, после которой фраза считается сказанной |
| `_WS_SEG_QUIET_MS` | 900 | пауза между сегментами в предложении |
| `_WS_GRACE_MS` | 2 500 | льготное окно после «конца» фразы |
| prefetch-поиск | TTL 180 с / таймаут 15 с | спекулятивный поиск по `query` из LLM |

Контекст LLM — 32768 токенов (`-c 32768` в llama.cpp), история диалога —
`ASSISTANT_HISTORY_SIZE` реплик с TTL.

## Ограничения

- Вместе с ПК доступен в интернет: основной сценарий — туннель `tunnel.py`
  (WSS :8443, свой сертификат с пиннингом), запасной — прямое подключение
  (IPv6 + DDNS, опционально IPv4 через проброс порта). Без настроенного DDNS
  и туннеля — только одна локальная сеть (телефон ↔ ПК).
- Ответы LLM короткие (1–2 предложения) — это специально: ассистент говорит
  вслух.
- Озвучка и остановка во время произношения управляются с телефона;
  барж-ин (перебивание) намеренно не реализован.
